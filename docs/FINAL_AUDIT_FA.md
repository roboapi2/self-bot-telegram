# گزارش نهایی مرحله دوم — ۲۰۲۶/۱۰/۱۱

به‌روزرسانی ممیزی ignore: قواعد واقعی `.gitignore` بررسی و تکمیل شد؛ بسته‌سازی اکنون فهرست صریح فایل‌ها دارد و فایل تازه در پوشه سورس را خودکار منتشر نمی‌کند. گزارش تفصیلی در `IGNORE_AUDIT_FA.md` و تاریخچه در `CHANGELOG.md` است. نسخه تازه `releases/ubcc-20261011-ignore-audit.tar.gz` با ۴۷ فایل سورس تولید شد؛ بسته ۴۲ فایلی پایین، نتیجه مرحله قبلی است و حفظ شده است. بررسی ۳۸ مسیر خصوصی و ۵۶ مسیر واجد نسخه‌بندی، تزریق فایل خصوصی ساختگی، تمام اعضای هر دو آرشیو و SHA-256 موفق بود. داده اصلی یا credential تغییر نکرده است. وضعیت تأیید نشده Ubuntu/Telegram همچنان برقرار است.

**وضعیت: سورس و روش استقرار اصلاح شده‌اند؛ تأیید آمادگی تولید هنوز مشروط به اجرای آزمون Ubuntu و چک‌لیست Telegram است.** محیط فعلی Windows بود. WSL نصب نبود، Docker/Podman در دسترس نبودند و دستگاه اتصال از راه دور نیز آفلاین بود. سرور Linux واقعی برای آزمون در دسترس قرار نگرفت؛ هیچ ادعای نصب موفق Nginx/FPM/systemd یا ورود Telegram مطرح نمی‌شود.

## اصلاحات انجام‌شده در همین پروژه

- نصب مجدد پیش از تغییرات از نصب موجود پشتیبان می‌گیرد و FPM/ناظر را متوقف می‌کند؛ مسیر سرویس و pool/site موجود پیش از تغییر بررسی می‌شود.
- هدف installer به Ubuntu 24.04 و PHP 8.3 مشخص محدود شد. CLI و FPM نسخه واحد دارند و قالب‌ها از مسیر صریح `/usr/bin/php8.3` استفاده می‌کنند.
- مالکیت کد، assets و vendor برای root و خواندن گروه ubcc تنظیم می‌شود؛ داده runtime خصوصی و قابل نوشتن برای ubcc است. فایل config موجود بازنویسی نمی‌شود.
- مهاجرت فهرست حساب‌ها همه فیلدها را حفظ می‌کند؛ اجرای دوباره فهرست فعال را عوض نمی‌کند. نشانگر مهاجرت مانع احیای خودکار داده قدیمی پس از گم‌شدن فهرست فعال می‌شود. JSON خراب، کلید نامعتبر و کلید تکراری با خطا رد می‌شوند و فایل موجود حفظ می‌شود.
- ناظر قفل تک‌نمونه دارد. کش stat در چرخه ناظر/بررسی worker و دریافت رمز 2FA پاک می‌شود تا تغییرات سایر پردازش‌ها دیده شوند. توقف سیگنال درون چرخه نیز رعایت می‌شود.
- doctor مسیر واقعی پروژه و امکان اجرای PHP CLI را بررسی می‌کند. فرمان‌های شروع/توقف گروهی در شکست کد خروج ناموفق می‌دهند.
- آزمون ساختگی Linux برای restart، جلوگیری از worker موازی، crash recovery و حفظ JSON توسعه یافت؛ اجرای آن در Windows صریحاً SKIP است.
- `scripts/validate-vps.sh` برای بررسی واقعی Composer، Nginx، FPM، systemd، مجوزها، مسیرهای خصوصی و logrotate آماده شد. `scripts/restore.sh` ورودی پشتیبان را از نظر traversal/link بررسی و پیش از restore از وضعیت فعلی پشتیبان می‌گیرد.
- update مستندات جدید را نیز منتقل می‌کند؛ config و داده از staging منتقل نمی‌شوند. releaseها از backup کنار گذاشته شده‌اند.
- پایان‌خط Windows در برخی اسکریپت‌ها در بررسی انتشار پیدا و به LF اصلاح شد؛ سازنده release اکنون CRLF اسکریپت/قالب را رد می‌کند. این بررسی مستقل از bash -n روی Windows است.
- پنل فارسی و مسیرهای قابلیت‌های موجود حفظ شدند؛ بازنویسی معماری یا جایگزینی پروژه انجام نشد.

نصب تازه موقت در تلاش اول به خطای ابزار 7-Zip موجود Windows برای symlink مستندات دو وابستگی برخورد کرد. پس از کنارگذاشتن مسیر آن ابزار در همان پردازش آزمایش، نصب با استخراج‌کننده جایگزین موفق شد. تنظیم دائمی سیستم یا lock برای دورزدن این خطا تغییر نکرد. PHP موقت Windows افزونه ZipArchive نداشت؛ installer Ubuntu افزونه php8.3-zip را نصب می‌کند. موفقیت تلاش دوم، اثبات نصب Ubuntu نیست.

خروجی بررسی‌های اصلی در `audit/phase2-verification.json` ذخیره شده است. حساب‌ها و تنظیمات ساختگی آزمون‌ها با داده واقعی متفاوت‌اند. پوشه `accounts/` اصلی در بررسی فعلی فایل runtime نداشت؛ بنابراین بقای نشست واقعی موجود عملاً قابل آزمون نبود. هیچ نشست واقعی ایجاد، حذف یا احراز نشد.

## ملاحظات و محدودیت‌های باقی‌مانده

۱. نصب/کنترل/backup/update از سرویس سراسری PHP 8.3 FPM استفاده می‌کنند و poolهای دیگر همان نسخه نیز در توقف تحت تأثیر قرار می‌گیرند. برای VPS اختصاصی طراحی شده‌اند. نام سرویس، socket و سایت ثابت است؛ یک نصب با این نام‌ها در هر سرور.

۲. تنظیمات `/etc` موجود به‌صورت خودکار بازنویسی نمی‌شوند. نسخه قدیمی با `/usr/bin/php` را با قالب جدید و دستورهای diff راهنمای عملیات بررسی کنید؛ validate-vps نسخه صریح PHP را نیز کنترل می‌کند. تنظیمات `/etc`، شبکه و SSH در backup برنامه نیستند.

۳. backup باید با توقف همه پردازش‌های وابسته انجام شود. کارگرهای قدیمی خارج systemd خودکار زیر پوشش این سرویس قرار نمی‌گیرند. نشست Telegram، API Hash و backup به‌اندازه رمز حساب حساس‌اند؛ لاگ قدیمی موجود نیز ممکن است خصوصی باشد و عمداً پاک نشده است.

۴. `restore` بازگشت عمدی به یک نقطه قدیمی است؛ وضعیت جاری قبل آن پشتیبان می‌شود. آرشیو دارای لینک/device رد می‌شود و برای آن بازیابی دستی بررسی‌شده لازم است. سالم‌بودن آرشیو جای اتصال واقعی نشست را نمی‌گیرد.

۵. فایل‌های JSON برای مقیاس محدود حساب‌ها مناسب‌اند؛ ارسال خارجی و ثبت وضعیت محلی تراکنش واحد نیستند. قطع برق بین ارسال و ثبت زمان ممکن است باعث ارسال تکراری شود. بازیابی حذف فقط برای داده قبلاً دریافت و ذخیره‌شده است. FLOOD_WAIT، دسترسی مقصد و محدودیت حساب Telegram همچنان اعمال می‌شوند.

۶. تغییر رمز پنل فوراً نشست‌های وب قبلی را باطل نمی‌کند. برای خروج اضطراری، در زمان توقف FPM تنها نشست‌های وب `.panel/sessions/` را طبق راهنما مدیریت کنید؛ نشست‌های Telegram متفاوت‌اند. logrotate با copytruncate احتمال از دست رفتن چند خط هم‌زمان دارد.

۷. بوت/QR/استقرار به دسترسی شبکه، ساعت صحیح سرور، فضای دیسک و حافظه کافی وابسته‌اند. خروج موفق Start در حالت supervisor به معنی ثبت درخواست است؛ وضعیت روشن واقعی و عملکرد Telegram باید جداگانه تأیید شوند.

## فعال‌سازی نهایی

۱. پوشه تمیز release را منتقل کنید یا نصب موجود را با داده‌ها به‌صورت امن مهاجرت دهید. ۲. config واقعی را روی VPS تنظیم کنید. ۳. نصب، doctor و سرویس‌ها را اجرا کنید. ۴. بررسی واقعی VPS را اجرا کنید. ۵. فقط با مجوز مالک حساب، چک‌لیست Telegram، crash/reboot و roundtrip پشتیبان را تکمیل و نتایج را ثبت کنید.

```bash
cd /opt/self
sudo bash scripts/install-vps.sh
sudo bash scripts/control.sh doctor
sudo systemctl enable --now userbot-supervisor
sudo bash scripts/validate-vps.sh
```

تا زمانی که موارد اجرا نشده بالا تکمیل و موفق ثبت نشوند، عبارت «آماده تولید و تأییدشده» برای این انتشار صحیح نیست. روش بدون دسترسی Linux طبق درخواست آماده شده است.
