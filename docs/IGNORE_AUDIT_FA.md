# ممیزی ignore و بسته‌سازی — ۲۰۲۶/۱۰/۱۱

یادداشت مرحله بعد: Docker و CI/CD اکنون اضافه شده‌اند؛ ادعای نبود Docker در این گزارش شرح زمان ممیزی قبلی است. نتایج و قواعد جدید در [ممیزی Docker](DOCKER_AUDIT_FA.md) آمده‌اند. Git اکنون موجود است و فهرست فایل‌های tracked نیز در قراردادهای جدید بررسی می‌شود.

## ساختار واقعی و فایل‌های یافت‌شده

اسکن بازگشتی بدون اعمال ignore انجام شد: پیش از تغییرات ۳۱۵۱ فایل، شامل ۲۹۵۳ فایل vendor و نسخه‌های انتشار قبلی. در ریشه فقط `.gitignore` موجود بود. فایل‌های `.gitignore` و `.gitattributes` داخل vendor متعلق به بسته‌های Composer هستند و تغییر نکردند. `.dockerignore`، `.ignore`، `.rgignore`، `.cursorignore` و فایل Docker/Compose در بررسی اولیه پروژه وجود نداشتند. تنها تنظیم محلی ابزار توسعه مشاهده‌شده `.claude/settings.local.json` بود؛ محتوای آن چاپ نشد.

پروژه روی Nginx/FPM/systemd مستقر می‌شود؛ Docker وارد معماری نشد و برای ابزارهای استفاده‌نشده ignore جدید ساخته نشد. تنها `.ignore` برای ripgrep که در همین گردش توسعه استفاده می‌شود اضافه شد؛ چون workspace بدون Git است، قواعد `.gitignore` در جستجوی معمول الزاماً فعال نیستند. `.ignore` همسان با `.gitignore` نگه داشته و در آزمون کنترل می‌شود. ابزارهای توسعه می‌توانند `.gitignore` را رعایت کنند، اما این رفتار وابسته به ابزار است و مرز امنیتی نیست.

## قواعد تغییرکرده

| قاعده | علت |
|---|---|
| `/config.php` و `/config.php.*` | تنظیم واقعی ریشه و کپی‌های محلی آن؛ `config.example.php` آزاد باقی می‌ماند |
| `.env` و `.env.*` با استثنای `!.env.example` | محیط‌های واقعی در هر پوشه کنار گذاشته می‌شوند؛ نمونه قابل بازبینی باقی می‌ماند |
| `/accounts/` و `/.panel/` | نشست، دیتابیس مرتبط، رسانه، آرشیو، وضعیت، PID، قفل، QR، رمز موقت و پشتیبان |
| `/accounts.json` و کپی‌های آن | فهرست واقعی قدیمی ریشه؛ نمونه پاک‌سازی‌شده در tests مخفی نمی‌شود |
| `session.madeline*`، `qr_2fa.secret*`، `qr_state.json`، PID و temp | نسخه سرگردان فایل‌های اجرای برنامه خارج از مسیر اصلی |
| لاگ و چرخش لاگ، `.bak` و `.backup` | فایل‌های محلی تولیدشده و کپی‌های پشتیبان |
| `/vendor/`، `/releases/`، `/backups/` | وابستگی دانلودشده، خروجی انتشار و پشتیبان محلی |
| `/backup_beta/` و `/extracted/` | قواعد مفید قبلی برای خروجی محلی قدیمی حفظ شدند؛ وجود آرشیو یا این پوشه‌ها فرض نشد |
| `/audit/` و کش Python | شواهد محلی شامل مسیر دستگاه/هش و خروجی تولیدشده؛ گزارش عمومی در docs می‌ماند |
| `/.claude/settings.local.json` | تنظیم شخصی مشاهده‌شده؛ فرمان‌های مشترک احتمالی `.claude/commands/` مخفی نمی‌شوند |
| `/graphify-out/*` با دو استثنای Markdown | داده و کش گراف تولیدشده کنار گذاشته می‌شود؛ ARCHITECTURE_FA.md و GRAPH_REPORT.md قابل نسخه‌بندی و بررسی می‌مانند |

قاعده کلی `*.lock` اضافه نشد: `composer.lock` ضروری است و باقی می‌ماند. سورس PHP، composer.json، نمونه تنظیمات، assets، deploy، scripts، tests، docs و CHANGELOG.md واجد نسخه‌بندی هستند. `.env.example` اکنون در workspace وجود ندارد و صرفاً برای این کار ساخته نشد؛ استفاده رسمی از `config.example.php` ادامه دارد. فایل `.env` نیز خودکار توسط برنامه بارگذاری نمی‌شود.

## سورس سفارشی حساب

در این workspace پوشه accounts هیچ فایل PHP سفارشی و هیچ فایل runtime نداشت. بنابراین کدی در این کار جابه‌جا یا حذف نشد. در نصب قدیمی ممکن است `accounts/<key>/bot.php` سفارشی باشد و درون خودش credential یا داده شخصی داشته باشد. برای محافظت از کل نشست و داده حساب، استثنای خطرناک `!accounts/**/*.php` اضافه نشد.

اگر سورس سفارشی دارید، فایل اصلی را حفظ کنید و یک **کپی دستی پس از بازبینی** در مسیر جدا مانند `legacy-src/reviewed-bot.php` نگه دارید. API/رمز/نام حساب/مقصد خصوصی را از کپی حذف و به تنظیمات منتقل کنید؛ تنها کپی تأییدشده را نسخه‌بندی کنید. این مسیر در Git قابل مشاهده است، اما release آن را خودکار شامل نمی‌کند. پس از تصمیم درباره ادغام قابلیت سفارشی در runner مشترک، فایل لازم را صریحاً به فهرست release و روش update اضافه و آزمون کنید. این کار اجازه انتشار خودکار همه PHPهای حساب را نمی‌دهد. برنامه موجود همچنان فایل سفارشی قدیمی را در ensure حذف نمی‌کند.

Fixtureهای JSON/PHP واقعاً پاک‌سازی‌شده می‌توانند در `tests/fixtures/sanitized/` بمانند؛ نام config.php یا accounts.json در این مسیر آزاد است چون قواعد اصلی به ریشه محدود شدند. نشست واقعی حتی با نام fixture نباید وارد تست یا مخزن شود.

## استقلال release از Git

`scripts/build-release.py` اکنون فقط فهرست **صریح فایل‌ها** را کپی می‌کند؛ فایل جدید در docs/scripts/assets/tests خودکار وارد بسته نمی‌شود. برای افزودن سورس جدید باید فهرست را بازبینی و اصلاح کنید. `.gitignore` و `.ignore` و CHANGELOG و مستندات جدید در بسته هستند. نمونه `.env.example` تنها در صورت وجود به فهرست اضافه می‌شود. تنظیم واقعی، account data، نشست، vendor، audit، graph، cache، backup و نسخه‌های انتشار از این فهرست بیرون‌اند. Symlink منبع و CRLF اسکریپت/قالب رد می‌شود.

بسته تازه `releases/ubcc-20261011-ignore-audit.tar.gz` است. بسته قدیمی `ubcc-20261011.tar.gz` حفظ شد و به‌عنوان نسخه قدیمی نیز بررسی می‌شود. نصب وابستگی‌ها از composer.lock انجام می‌شود؛ vendor لازم نیست همراه انتشار باشد. ignore در تصمیم بسته‌سازی دخالت ندارد و داده runtime در workspace حذف نمی‌شود.

## روش اعتبارسنجی

workspace مخزن Git نیست (`git rev-parse` این را تأیید کرد) و Git مقداردهی نشد. از موتور قواعد Git در ripgrep با `--no-require-git` روی پوشه موقت ساختگی استفاده می‌شود؛ بنابراین این نتیجه معادل اجرای `git check-ignore -v` در یک مخزن واقعی ادعا نمی‌شود.

آزمون اختیاری توسعه:

```bash
python3 tests/ignore_release.py --archive releases/ubcc-20261011.tar.gz --archive releases/ubcc-20261011-ignore-audit.tar.gz
```

این تست به Python و ripgrep نیاز دارد؛ جزو نیازهای اجرای برنامه یا installer نیست. در Ubuntu برای اجرای این آزمون توسعه، `sudo apt-get install -y ripgrep` کافی است. تست ۳۸ مسیر خصوصی و ۵۶ مسیر سورس/نمونه/fixture را جداگانه در هر دو حالت Git-style و جستجوی پیش‌فرض `.ignore` بررسی می‌کند. fixture موقت از سورس مجاز ساخته می‌شود؛ داده ساختگی خصوصی در پوشه‌های مجاز تزریق و اثبات می‌شود وارد release نمی‌شود. فایل‌های واقعی accounts/config در fixture کپی نمی‌شوند.

آرشیوها واقعاً باز و تمام memberها، نوع مسیر، عضویت در allowlist، manifest، SHA-256 هر فایل و SHA-256 کل آرشیو بررسی می‌شوند. مقادیر literal بلند شناخته‌شده API Hash/رمز از config محلی فقط در حافظه برای تطبیق استفاده می‌شوند؛ مقادیر چاپ یا منتشر نمی‌شوند و PHP تنظیمات اجرا نمی‌شود. این اسکن همه شکل‌های credential، رمز کوتاه، مقدار محیطی یا اطلاعات خصوصی دلخواه داخل سورس را کشف نمی‌کند؛ بازبینی انسانی همچنان لازم است.

نتیجه اجرای واقعی روی Windows: هر ۳۸ مسیر ignored و ۵۶ مسیر واجد نسخه‌بندی مطابق انتظار بود. fixture بسته‌سازی ۴۸ فایل تأییدشده داشت؛ یک `.env.example` ساختگی در آن اضافه شده بود و release واقعی ۴۷ فایل دارد. محتوا و SHA-256 تمام فایل‌های بسته قدیمی ۴۲ فایلی و بسته تازه ۴۷ فایلی و checksum کل هر دو آرشیو موفق بررسی شد؛ مسیر غیرمجاز یا تطبیق credential بلند شناخته‌شده یافت نشد. syntax Python و Bash اسکریپت update نیز موفق بود. هش فایل‌های واقعی config.php، accounts.json و MadelineProto.log تغییر نکرد و runtime حساب‌ها همچنان صفر فایل داشت.

## محدودیت و نگهداری

- `.gitignore` فایل tracked یا تاریخچه Git را حذف نمی‌کند. چون این workspace مخزن نیست، فهرست tracked/history قابل بررسی نبود. در مخزن مقصد، `git ls-files -- config.php accounts.json accounts .panel` را بررسی کنید. در صورت وجود، ابتدا نسخه امن محلی نگه دارید و حذف از index با `git rm --cached` را آگاهانه انجام دهید؛ برای پوشه‌ها گزینه `-r` فقط همراه `--cached` استفاده شود. تغییر یا بازنویسی تاریخچه بدون تصمیم مالک انجام نشده است. credential واقعاً منتشرشده باید تعویض/لغو شود.
- ignore مانع دانلود وب، دسترسی سیستم یا خواندن مستقیم توسط AI نیست. Nginx allowlist، auth/CSRF API و مجوزهای فایل مستقل هستند. ابزار جستجو با override می‌تواند فایل ignored را بخواند؛ آن‌ها را به سرویس خارجی ارسال نکنید.
- سورس جدید، fixture و مثال تنظیمات باید پیش از اضافه‌شدن به allowlist از نظر داده خصوصی بازبینی شوند. پشتیبان دستی با نام دلخواه خارج مسیرهای تعریف‌شده تضمیناً ignored نیست؛ آن را در مسیر خصوصی backup نگه دارید.
- آزمون Ubuntu/systemd/Telegram این مرحله اجرا نشد؛ قواعد ignore و آزمون بسته‌سازی جای آن‌ها را نمی‌گیرند.

فایل‌های این مرحله: `.gitignore`، `.ignore`، `scripts/build-release.py`، `scripts/update.sh`، `tests/ignore_release.py`، `CHANGELOG.md`، همین گزارش، `docs/FINAL_AUDIT_FA.md` و مسیر نسخه تازه در راهنماهای نصب/عملیات. شواهد محلی آزمون‌ها در `audit/ignore-verification.json` نگه داشته می‌شود و در انتشار نمی‌آید.
